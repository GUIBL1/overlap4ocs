 HTSim OCS standalone backend

[中文说明](README_CN.md)

`htsim_ocs` is the standalone optical circuit switching (OCS) simulation backend for overlap4ocs. It reads a complete, deterministic JSON executionplan and produces a formal JSON result plus an optional operation-event JSONL trace:

```text
Plan v2 JSON -> htsim_ocs -> Result v2 JSON (+ optional operation-event JSONL)
```

## Implemented capabilities

`htsim_ocs` receives a schedule already generated by overlap4ocs, executes it in HTSim's event-driven simulation environment, and returns the simulation result to overlap4ocs. It mainly adds the following capabilities.

### Read a complete overlap4ocs schedule

- Receive topology, optical-plane configurations, flows, execution steps, step dependencies, and reconfiguration schedules through a fixed JSON format.
- Before simulation, check that the input is complete, that related fields are consistent, and that every flow can reach its destination under the assigned configuration. Invalid input produces an explicit error immediately.
- The scheduling algorithm remains the responsibility of overlap4ocs; the backend executes only what is explicitly specified in the input file.

### Simulate multiple independent optical planes

- Create independent switching, transmission, and reconfiguration state for every optical plane in HTSim.
- Each optical plane may use a different current configuration and may begin and finish reconfiguration at different times.
- While one optical plane is reconfiguring, other planes can continue transferring data. This captures the core SWOT behavior of overlapping transmission and reconfiguration across multiple planes.
- Before changing configuration, an optical plane waits for all data already sent on that plane to finish, preventing traffic from an old configuration from entering a new one.

### Execute the three schemes compared in the paper

- One-shot configuration: install a fixed configuration before simulation and perform no further reconfiguration during the collective.
- One reconfiguration per step: after the current step finishes, switch all required configurations for the next step and then begin its transmission.
- SWOT: each optical plane reconfigures early according to its own usage; while some planes reconfigure, other planes may continue sending ready data.

All three schemes use the same flow execution and result-accounting logic, so their collective completion times can be compared directly.

### Execute flows and step dependencies from the plan

- Place each input flow on its assigned optical plane and advance simulation time according to that plane's bandwidth, propagation latency, and
  reconfiguration delay.
- Support a global barrier across all steps as well as explicit predecessor dependencies between flow groups supplied by overlap4ocs.
- A dependent flow group or step starts only after its prerequisite data has actually arrived at the receiver.
- Use the arrival time of the last required flow at its receiver as the collective completion time.

### Support both small-scale checks and paper-scale simulations

- `full_packet` simulates packets one by one and is mainly intended for small-scale correctness checks.
- `exact_coalesced` processes consecutive packets in batches, reducing the event count and memory consumption of paper-scale cases.
- Both modes use the same traffic, timing, and completion rules. Equivalence tests verify that their main simulation results agree.

### Produce directly consumable results

- Produce a fixed-format result JSON containing the collective completion time, completion state of every step and flow, configuration and
  reconfiguration timing for every optical plane, and traffic statistics.
- Optionally produce a time-ordered operation trace for inspecting the order of flow release, step completion, and optical-plane reconfiguration.
- Input errors, runtime deadlocks, and exceeded simulation limits produce structured failure information instead of being presented as valid collective completion times.
- The same program and input produce consistent results, supporting repeatable experiments, retained evidence, and comparisons among the three schemes.

## What this backend does not do

The following capabilities belong to upstream overlap4ocs and are not hidden backend behavior:

- define collective algorithms, rank partners, data-block ownership, or reduction semantics;
- run a mixed-integer linear program or planner, or select baseline, one-shot, or SWOT parameters;
- decide whether a one-shot configuration is feasible or generate an unsupported certificate;
- convert a collective and planner assignment into explicit flows, flow groups, tokens, configurations, and optical-plane programs;
- reinterpret results, clamp collective completion time, or fall back to an analytical model after failure.

Tip: the backend simulates a lossless, payload-only transport model. It does not simulate retransmission, packet loss, priority flow control, or similar mechanisms.

## Runtime path

```text
raw plan bytes
  -> CLI path/I/O preflight and SHA-256
  -> strict Plan v2 parser and semantic validation
  -> immutable OcsExecutionPlanV2
  -> OcsCoordinator
       -> token/group/step dependency runtime
       -> one OcsPlaneRuntime per plane
            -> program epochs and reconfiguration timer
            -> one OcsPlaneDataplane per plane
                 -> one serializer per source
                 -> OCS switch -> destination Pipe -> receiver
  -> OcsRunSummary + operation events
  -> canonical Result/JSONL writer
  -> atomic trace commit, then atomic result commit
```

A successful collective completion time starts at the collective-start token at `0 ps` and ends when the final required payload byte reaches its receiver.

## Build

Use Python 3.10+, a C++17 compiler, GNU Make, and the corresponding Conda environment. Run from the repository root:

```bash
source "$(conda info --base)/etc/profile.d/conda.sh"
conda activate ocs
make -C simulator/htsim_ocs clean all
```

The production executable is located at:

```text
simulator/htsim_ocs/build/htsim_ocs
```

Inspect the exact build information and contract identity:

```bash
simulator/htsim_ocs/build/htsim_ocs version
simulator/htsim_ocs/build/htsim_ocs capabilities --json
```

Run the complete backend acceptance gate:

```bash
make -C simulator/htsim_ocs \
  test check-link-closure check-vendor
```

## CLI usage

```text
htsim_ocs run --plan PATH --result PATH [--trace PATH]
htsim_ocs validate --plan PATH
htsim_ocs capabilities --json
htsim_ocs version
htsim_ocs help
```

### Validate an execution plan

```bash
simulator/htsim_ocs/build/htsim_ocs validate \
  --plan simulator/htsim_ocs/tests/fixtures/v2/runtime/paper_fig5_swot/plan-exact-coalesced.json
```

`validate` reads the raw bytes and performs all schema, semantic, capacity, cycle, path, program-epoch, dependency, and provenance checks without starting the simulation.

### Run an execution plan

```bash
run_dir="$(mktemp -d)"

simulator/htsim_ocs/build/htsim_ocs run \
  --plan simulator/htsim_ocs/tests/fixtures/v2/runtime/paper_fig5_swot/plan-exact-coalesced.json \
  --result "$run_dir/result.json" \
  --trace "$run_dir/operations.jsonl"
```

Rules:

- `--plan` and `--result` are required; `--trace` is optional.
- The execution plan must be a readable regular file.
- Output parent directories must already exist and be writable.
- Plan, result, and trace paths must be distinct.
- Result and trace targets must not already exist; the backend never overwrites formal output.
- The CLI cannot override the execution mode, random seed, dependency policy, path policy, maximum simulation time, or maximum event count.
- Do not parse status or collective completion time from standard output or standard error; read and validate the formal result file.

### Exit classes

| Exit | Meaning                                  | Typical formal stop reason                   |
| ---: | ---------------------------------------- | -------------------------------------------- |
|    0 | Success                                  | `collective_complete`                      |
|    2 | Invalid or unsupported input             | `invalid_input`, `unsupported_semantics` |
|    3 | Runtime deadlock or invariant failure    | `deadlock`, `invariant_violation`        |
|    4 | Execution-plan simulation budget reached | `max_simulation_time`, `max_event_count` |
|    5 | I/O or internal failure                  | `io_error`, `internal_error`             |

If the result path itself cannot be committed, a nonzero exit code and standard error may be the only diagnostic. Other known failures produce a structured Result v2 with a null collective completion time.
